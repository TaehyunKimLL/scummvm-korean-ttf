# SVFN — ScummVM CJK 비트맵 폰트 포맷

기존 팬번역 `.fnt` 는 4바이트 머리말 뒤에 1bpp 글리프를 늘어놓은 것이
전부다. 안티에일리어싱을 담을 수 없고, 글자마다 폭을 달리할 수도 없고,
글리프가 몇 개인지 어느 인코딩인지도 파일 안에 적혀 있지 않다.

SVFN 은 그 세 가지를 채운다. 8bpp 알파, 글자별 전진 폭, 자기 서술.

## 1. 기존 포맷과의 관계

기존 파일은 그대로 읽힌다. 판별은 첫 4바이트로 한다.

| 첫 4바이트 | 해석 |
|---|---|
| `"SVFN"` | 이 문서의 포맷 |
| 그 외 | 기존 포맷 (첫 바이트는 항상 2) |

검증한 34개 팬번역 `.fnt` 는 예외 없이 첫 바이트가 2 였고 파일 크기도
`((width+7)/8) * height * 2350 + 4` 와 정확히 일치했다. 두 포맷이 섞일
일은 없다.

## 2. 머리말 (32바이트)

정수는 전부 리틀엔디언이다.

| 위치 | 크기 | 이름 | 설명 |
|---|---|---|---|
| 0 | 4 | `magic` | `"SVFN"` |
| 4 | 2 | `version` | 1 |
| 6 | 2 | `flags` | 아래 표 |
| 8 | 1 | `bpp` | 1 또는 8 |
| 9 | 1 | `shadow` | 기존 그림자 방식 0~3, 없으면 0xFF |
| 10 | 2 | `codePage` | 949 · 932 · 936 · 950, 또는 0 |
| 12 | 2 | `glyphCount` | 글리프 수 |
| 14 | 1 | `cellWidth` | 셀 폭. 고정폭이면 전진 폭이기도 하다 |
| 15 | 1 | `cellHeight` | 셀 높이 |
| 16 | 1 | `ascent` | 셀 위쪽에서 기준선까지 |
| 17 | 1 | `reserved0` | 0 |
| 18 | 2 | `reserved1` | 0 |
| 20 | 4 | `metricsOffset` | 글자별 폭 표의 위치. 고정폭이면 0 |
| 24 | 4 | `dataOffset` | 글리프 데이터의 위치 |
| 28 | 4 | `dataSize` | 글리프 데이터의 길이 |

### flags

| 비트 | 뜻 |
|---|---|
| 0 | 가변폭. `metricsOffset` 에 표가 있다 |
| 1 | 글리프가 낱자다. 실행 중에 조합한다 (2단계에서 사용) |

`codePage` 가 0 이면 글리프 순서를 파일이 정하지 않는다는 뜻으로, 호출
쪽이 이미 알고 있는 순서를 쓴다.

## 3. 글자별 폭 표

`flags` 비트 0 이 서 있을 때만 존재하고, `glyphCount` 개의 4바이트
항목이 이어진다.

| 위치 | 크기 | 이름 | 설명 |
|---|---|---|---|
| 0 | 1 | `advance` | 다음 글자까지 펜이 나아가는 거리 |
| 1 | 1(부호) | `bearingX` | 펜에서 잉크 왼쪽 끝까지 |
| 2 | 1 | `inkWidth` | 잉크의 실제 폭 |
| 3 | 1 | `reserved` | 0 |

**셀 자체는 언제나 `cellWidth × cellHeight` 로 고정이다.** 가변폭이란
전진 폭이 글자마다 다르다는 뜻이지 저장 크기가 다르다는 뜻이 아니다.
덕분에 i 번째 글리프의 위치는 곱셈 한 번으로 나온다.

## 4. 글리프 데이터

`glyphCount` 개의 셀이 위에서 아래로, 왼쪽에서 오른쪽으로 늘어선다.

```
glyphStride = (bpp == 1) ? ((cellWidth + 7) / 8) * cellHeight
                         : cellWidth * cellHeight

i 번째 글리프 = dataOffset + i * glyphStride
```

- **1bpp** — 한 행이 `(cellWidth+7)/8` 바이트. 최상위 비트가 왼쪽 픽셀.
- **8bpp** — 한 행이 `cellWidth` 바이트. 값은 덮임 정도 0~255.

8bpp 값은 그대로 알파로 쓴다. 0 은 완전 투명, 255 는 완전 불투명이다.
게임 팔레트와 섞는 일은 합성 단계가 맡는다.

## 5. 글리프 순서

`codePage` 가 정한다. 완성형 2350자(CP949)면 기존 팬번역과 같은 순서다.

```
codePage 949:  idx = (hi - 0xB0) * 94  + (lo - 0xA1)
codePage 932:  idx = (hi < 0xE0 ? hi - 0x81 : hi - 0xC1) * 188
                     + (lo < 0x7F ? lo - 0x40 : lo - 0x41)
codePage 936:  idx = (hi - 0x81) * 191 + (lo - 0x40)
codePage 950:  idx = (hi - 0x81) * 191 + (lo - 0x40)
```

`idx` 가 `glyphCount` 를 넘으면 그 글자는 없는 것으로 친다.

## 6. 만드는 법

`scripts/mkfont.py` 가 TTF 에서 구워낸다.

```bash
# 16x16 고정폭, 안티에일리어싱 없음 (픽셀 폰트를 그대로 뜬다)
python3 scripts/mkfont.py neodgm.ttf out.fnt --size 16 --bpp 1

# 24x24 8bpp 알파, 가변폭
python3 scripts/mkfont.py NanumGothic.ttf out.fnt --size 24 --bpp 8 --variable

# 일본어
python3 scripts/mkfont.py misaki.ttf out.fnt --size 16 --codepage 932
```

굽는 쪽이 FreeType 을 쓰므로, 게임을 돌리는 빌드에는 FreeType 이 없어도
된다. 이것이 이 포맷의 존재 이유다.

## 7. 왜 이렇게 했나

**셀 크기를 고정한 이유** — 글리프마다 크기가 다르면 위치를 찾는 데 표를
한 번 더 뒤져야 한다. 2350자를 매 프레임 그리는 경로라 곱셈 한 번으로
끝나는 편이 낫다. 8bpp 24×24 로 2350자를 담아도 1.3MB 이고, 요즘 기준
문제될 크기가 아니다.

**높이를 글자마다 두지 않은 이유** — 같은 이유다. 모든 글리프가 셀
높이를 다 쓰고, 기준선은 폰트 전체가 하나를 공유한다. 조판이 아니라
고정 행 높이의 게임 자막을 그리는 용도다.

**매직을 붙인 이유** — 기존 포맷은 첫 바이트가 2 라는 사실 말고는 자기를
설명하지 않는다. 크기로 글리프 수를 역산해야 했고 인코딩은 짐작해야
했다. 같은 실수를 반복하지 않으려고 머리말에 다 적었다.
