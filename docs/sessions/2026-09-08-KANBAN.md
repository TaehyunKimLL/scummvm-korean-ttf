## Backlog

**B1. `CharsetRendererV7` / `CharsetRendererNut` have no hook.** FT, The Dig
and CMI draw through `TextRenderer_v7::drawString` →
`CharsetRendererV7::draw2byte` / `::drawCharV7`, none of which mention
`_hiResText`. Proven 2026-09-06: with a map read and both fonts loaded, the
log has zero `HRTEXT` lines and the frames are byte-identical to the
control. Needs new hooks plus `getCharWidth` for the advances.

**B2. Mac is a different shape.** `CharsetRendererMac::printChar` draws each
glyph twice — into `_textSurface` at colour 0 as a stencil, and into
`_macScreen` with the real colour. Handing that stencil to the layer would
write colour 0 over every glyph. What Mac could gain is antialiasing and
replacement faces, which means changing the renderer's glyph source, not the
compositor.

**B3. `scrollEffect` four directions** (`gfx.cpp:5023, 5057, 5094, 5130`).
Upstream code, unreachable in the v5 games measured (0 hits across three
targets), and its source and destination coordinates differ so it cannot be
expressed through `drawStripToScreen`. Left alone deliberately.

**B4. `drawBits1Kor` bottom-right scale boundary** — raised by an external
review, never investigated.

**B5. Window size on a refused font set.** When the whole-multiple rule
rejects a set, the layer resets but the backend window has already been
sized. Measured harmless — 700x525 is the aspect-corrected 320x200, not a 2x
window — but the ordering of `resolveScale` against `initGraphics` is worth
a second look.

**B6. `mkfont.py --ink-advance` is uncommitted** in
`~/src/scummvm-korean-ttf`. Adds ink-based advances for CJK faces that
report one advance for every glyph.

## Corrections worth keeping

Each of these was a wrong conclusion of mine that a measurement or the user
overturned. They are here so the same mistake is not made twice.

- **"Latin ratios are non-uniform, 1.71 to 2.25."** Wrong. The cells were
  identical; I divided the CJK cell by the double-byte grid and the Latin
  cell by the game's charset height, which are different numbers.
- **"FM-Towns ROM font replacement works."** Wrong. The fonts loaded and
  the log looked right while every Japanese glyph still came from the ROM.
  The user spotting that only the digit `2` had an outline is what exposed
  it.
- **"The colour must be fixed when loading the font."** Wrong layer twice
  over: a `.fnt` holds coverage and no colour, and the difference was a
  missing decoration rather than a wrong colour.
- **"Scale from the largest multiple that matches."** Wrong. A 24px font of
  a 12px charset is also 8×3, so it read as 3x. Smallest match is correct.
- **Counters are not proof.** `KRAW=0` once looked like success while the
  process was dying on an assert. A pass needs the frame as well as the
  count.
