## S1 회귀 검증 기록 (2026-09-05)

19 타깃 × 2 시점 = 38 캡처를 대조군과 비교했다.

첫 비교에서 `i4-multi_t30` 이 2,909px / 하단 18행으로 회귀 후보에 걸렸다.
육안 확인 결과 **인트로 크레딧 스크롤의 위치 차이**였고, 글꼴·글자 모양은
세 캡처 모두 같았다 ("프로그래밍 : 토니 시에").

다만 그때는 대조군 두 런이 서로 0px 로 일치해 "우연"으로 넘길 수 없었다.
재실행으로 갈랐다:

```
base1 vs base3 :    0     대조군끼리 일치
base3 vs s1r2  :    0     S1 재실행이 대조군과 완전 일치   ← 결정적
s1    vs s1r2  : 2909     S1 의 두 런끼리 다름
```

빌드 차이라면 `base3 vs s1r2` 가 0 일 수 없다. **실행 편차**이며, `i4-multi`
가 유일하게 `korean_ttf_map` 이 설정된 타깃이라 S1 이 실제로 맵 파일을 읽어
시작 시각이 몇 프레임 밀린 것이다.

전체 재비교 결과 **회귀 0 건**.

교훈: 시간 기준 캡처는 "회귀 후보 1건"을 만들어낼 수 있다. 한 번의 비교로
판정하지 말고, 양쪽을 각각 두 번 돌려 네 조합을 볼 것. 근본 해결은 프레임
기준 덤프(`fbdump.sh`)이며, 실제로 그리기 시작하는 S3 부터는 그쪽을 쓴다.

### 회귀 판정 — 시간 기준 캡처의 한계를 확인

`i3-2x_t30` 이 83,416px 차이로 회귀 후보에 걸렸다. 육안 확인 결과 글꼴·글자
모양은 동일하고 **기차 인트로의 가로 스크롤 위치**만 달랐다. 시프트 보정으로
확정:

```
base3 vs s2   : 최적 시프트 -16px -> 잔차 2,712px
base1 vs base3: 최적 시프트  +0px -> 잔차 2,712px   ← 대조군끼리의 잔차와 동일
```

같은 바이너리(S2)를 두 번 돌린 비교에서도 다른 타깃(`en-dig_t40`)이 후보로
걸려, 판정 규칙 자체의 오탐임이 드러났다.

`~/games/scrollcheck.sh` 를 만들어 각 빌드를 4 회씩 돌려 분포를 쟀다:

```
within A (대조군끼리) n=6   min=      0  max= 82,912
within B (S2 끼리)    n=6   min=    732  max= 85,144
A vs B               n=16   min=      0  max= 84,448
```

**A/B 사이에 0px 일치 쌍이 있고**, 같은 바이너리끼리도 8 만 px 씩 벌어진다.
같은 모집단이며 렌더링 차이가 아니다.

교훈: 스크롤 장면에서 시간 기준 캡처는 한 번의 비교로 판정할 수 없다.
빌드마다 여러 번 돌려 **분포끼리** 비교해야 한다.

### 프레임 기준 덤프로 재확인 — 시간 기준의 결론을 검증

`dbgfiles.sh` 를 고친 뒤(아래) 같은 비교를 프레임 기준으로 다시 했다.
`i3-2x` 프레임 600, S1 빌드 vs S2 빌드:

```
meta A:  FRAME 600 room=1  vs0 ... xstart=536
meta B:  FRAME 600 room=1  vs0 ... xstart=536    ← 스크롤 위치까지 동일

f600_text.bin  same        ← hi-res 텍스트 오버레이 완전 일치
f600_vs1.bin   same
f600_vs2.bin   same
f600_vs3.bin   same
f600_vs0.bin   106 바이트 차이 (40,960 중)
```

시간 기준에서 83,416px 이던 차이가 프레임 기준에서는 **`xstart` 까지 일치**해
사라졌다. 남은 106 바이트는 320×128 화면에 행당 4~5 개씩 흩어져 있어
(x 32~256, y 54~108) 텍스트 교체의 형태가 아니다. 육안 확인 결과 **박물관
장면의 인물 스프라이트 위에만** 차이가 있고 배경·선반·기둥은 완전히 동일,
글자는 화면에 아예 없다. 캐릭터 애니메이션 프레임 차이다.

`_textSurface` 가 바이트 단위로 같다는 것이 S2 의 직접적 증거다.

### `dbgfiles.sh` 수정

프레임 덤프가 빈 채로 끝나던 원인은 도구였다. `dbgfiles.sh gfx.cpp` 처럼
**경로 없이** 넘기면 `engines/scumm/` 을 붙이지 않아 아무것도 재컴파일하지
않고, 그런데도 성공한 것처럼 끝났다. GDB 로그에는 `No symbol table is loaded`
와 `Breakpoint 1 pending` 만 남는다.

고친 내용:
- 인자를 실제 파일로 해석 (없으면 `engines/scumm/` 아래를 찾고, 그래도 없으면 실패)
- 컴파일·링크 실패를 종료 코드로 전파
- **`readelf --debug-dump=info` 로 심볼이 실제로 들어갔는지 확인**하고,
  없으면 `symbols missing, do not trust a dump` 로 실패

이제 `symbols OK: engines/scumm/gfx.cpp` 가 찍히고 브레이크포인트가
`Breakpoint 1 at 0x5f8665: file engines/scumm/gfx.cpp, line 551` 로 붙는다.

### 배율 충돌 — 사용자 질문에 대한 실측

"FM-Towns 처럼 원래 배율이 있으면 2×2=4배가 되나?"

**되지 않는다.** 곱하지 않고 **대체**하며, 플랫폼이 이미 배율을 정했으면
hi-res 쪽이 물러선다. `~/games/multcheck.sh` 로 측정:

| 타깃 | 강제 hi-res scale | 백엔드 해상도 |
|---|---|---|
| `ja-mi2` (FM-Towns) | 없음 | 640×400 |
| `ja-mi2` (FM-Towns) | **3** | **640×400** — 무시 |
| `en-mi1towns` (FM-Towns) | **3** | **640×400** — 무시 |
| `mi2-svfn` (PC 한국어) | 없음 | **960×600** |

FM-Towns 타깃에 맵까지 붙여 진짜로 충돌시키면 경고가 남는다:

```
SCUMM: hi-res text enabled, scale 3, alpha 1
WARNING: this platform already scales text by 2; ignoring the hi-res scale of 3
Setting 640 x 400 -> 640 x 400
```

**통합하지 않는 이유**: FM-Towns 의 2배는 단순 배율이 아니라 **두 번째
하드웨어 텍스트 레이어의 에뮬레이션**이다 — `_townsScreen`, 레이어별
`clearLayer()`, `towns_fillTopLayerRect()`, `drawStripToScreen()` 내 전용 분기.
hi-res 는 한 장의 큰 서피스에 그려 합성하는 방식이라 모델이 다르고, 두 배율을
곱하면 어느 경로도 합성할 줄 모르는 크기가 된다.

**대가**: FM-Towns 게임은 hi-res 배율을 쓸 수 없다. 없애려면 Towns 레이어
경로 자체를 재작업해야 하며, 이는 설계 문서의 "하지 않을 것"에 있는
`drawStripToScreen` 재구조화와 같은 범위다.

### 순서 의존 발견

`loadCJKFont()` 가 `charset.cpp:146` 에서 `_textSurfaceMultiplier = 1` 로
되돌린다. 실행 순서는 `loadCJKFont`(1274) → FM-Towns(1277) → **hi-res(1286)**
이므로 현재는 안전하지만, 숨은 결합이다. hi-res 가 **마지막이어야 한다**는
것을 주석으로 명시했다.

### `dbgfiles.sh` 수정 (프레임 덤프 복구)

`dbgfiles.sh gfx.cpp` 처럼 경로 없이 넘기면 `engines/scumm/` 을 붙이지 않아
아무것도 재컴파일하지 않고도 성공한 것처럼 끝났다. 그 결과 GDB 가
`No symbol table is loaded` 로 브레이크포인트를 못 걸고 덤프가 비었다.
경로 보완 + 실패 전파 + **`readelf` 로 심볼 확인** 을 넣었다.

## 텍스트 케이스 목록 (2026-09-06 실측)

인트로 자막 하나만 캡처하면 렌더링의 1/6만 검증된다. `~/games/uidrive.sh` 로
게임을 각 상황까지 몰고 `~/games/textcases.py` 로 분류한 결과(mi2-svfn):

**charset 하나로는 상황이 특정되지 않는다 — (charset, vs) 쌍이어야 한다.**

| charset | vs | 정체 | 바이트 |
|---|---|---|---|
| 1 | 0 | **엔진 메뉴** — `Save Load Play Quit` | 전부 1바이트 |
| 1 | **2** | **문장줄** — "걸어가기", "관찰하기 금은보화" | 1B 37, 2B 107 |
| 2 | 0 | **대사/자막** | 1B 22, 2B 55 |
| 4 | 0 | **장소 이름** — "카리브 해 심연의", "스캡 섬" | 1B 5, 2B 10 |
| 6 | 0 | **동사줄** | 전부 2바이트 |
| 6 | 2 | **동사줄** (동사 화면) | 전부 2바이트 |
| 7 | 0 | **인트로/선택 화면** | 1B 39, 2B 50 |

세 가지가 분명해졌다:

- **charset 1 은 "라틴 메뉴"가 아니다.** vs=0 에선 메뉴를, **vs=2 에선 문장줄**을
  그리며 후자는 대부분 한글이다. 처음엔 "menu (Latin)"으로 적었으나 세이브
  기반 런에서 오류가 드러났다. 목표 1(라틴 hi-res)이 걸리는 건 vs=0 쪽이다.
- **charset 6 은 두 개의 virtscreen(0, 2)에 걸친다.** charset 만으로 분기하면
  동사줄의 절반을 놓친다.
- **동사줄을 뺀 모든 케이스가 바이트 폭을 섞는다.** 대사가 22/55 이므로,
  1바이트 가정은 예외 상황이 아니라 평범한 문장에서 깨진다.

### 프레임 번호를 찾지 않는다

처음엔 프레임 200/900/1200 을 덤프해 글자를 찾으려 했고 **전부 빈 텍스트
서피스**였다. 어느 프레임에 대사가 있는지는 실행 속도에 달려 있어 런마다

### 바이트 순서 — 사용자 질문에서 나온 실측

`decodeNext()` 에 넘길 때 어느 쪽이 lead byte 인가. 스왑을 뒤집어봤지만 출력이
전혀 안 바뀌어 파고든 결과, **진짜 원인은 순서가 아니었다**:

```
WARNING: encoding.dat is not found. Support for CJK is disabled!
```

변환 테이블이 없어 모든 글자가 U+FFFD 였다. 테이블을 붙인 뒤에야 두 순서가
구분됐고, **원래 코드(low half 가 lead byte)가 옳았다**:

| 값 | lo-first | hi-first |
|---|---|---|
| 0xB1BC | **선** | 굴 |
| 0xC3C5 | **택** | 쳔 |
| 0xCFC7 | **하** | 逑(한자) |
| 0xE4BF | **요** | 岳(한자) |

**엔디안 독립이다.** `charset.cpp:547` 이 `chr = text[pos++] | (chr << 8)` 로
**산술로** 조립하고, 우리도 `chr >> 8` / `chr & 0xFF` 로 되돌린다. 메모리
레이아웃을 읽는 곳이 아니므로 빅엔디안에서도 같은 값이다. 주석에 명시했다.

`runlog.sh` / `fbdump.sh` / `uisnap.sh` / `fbtext.sh` 모두 `extrapath` 를
자동 설정하도록 고쳐 이 함정이 재발하지 않게 했다.

### 32bpp 협상 — 백엔드 이름이 아니라 능력으로

```
opengl:  SCUMM: hi-res text blending into ABGR8888@4
surface: WARNING: no 32bpp screen available (got CLUT8); will not be blended
```

둘 다 **계속 실행된다**. 못 얻으면 조용히 블렌딩만 끈다.

`kFeatureOpenGLForGame` 으로 분기했으면 틀렸을 것이다 — 그 플래그는 3D
렌더링용이라 `surface` 모드에서도 `yes` 로 나온다(실측). 우리가 묻는 건
"지금 32bpp 화면을 받을 수 있나"이고, 그건 `getSupportedFormats()` 로만 알 수
있다. 이 머신에서 SurfaceSDL 이 32bpp 를 못 주는 이유도 백엔드 자체가 아니라
X 화면이 `RGB888`(알파 없음)이라 유도 목록이 비기 때문이다.

`_compositeBuf` 크기도 실측 확인:

```
opengl:  960x600 x 4bpp = 2,304,000 bytes, alphaActive=1
surface: 960x600 x 1bpp =   576,000 bytes, alphaActive=0
```

### stride 버그 — "블렌딩 실패"처럼 보였던 것

첫 합성 화면이 **가로 3회 타일링 + 세로 전단**으로 나왔다. 블렌딩 문제로
보였지만 아니었다. `copyRectToScreen()` 에 `width * bytesPerPixel` 을
넘겼는데, 합성 버퍼는 행마다 `width * m` 픽셀을 담는다. 백엔드가 각 행을
다음 행 1/3 지점부터 읽어 그림이 옆으로 반복되고 기울어진 것이다.

기억할 형태: **기하가 틀리면 stride, 색이 틀리면 팔레트.** 스크린샷을 처음
볼 때 둘은 비슷해 보이지만 원인이 전혀 다르다.

### 육안 검증 (실제 화면 캡처, `alphashot.sh`)

일어나므로 **실제 창을 캡처해야** 확인된다.

## S6 검증 기록 — 커서 (2026-09-06)

커서는 **백엔드가 그리는 별도 레이어**라 스크린샷에 안 잡힌다. 그래서 두 버그가
숨어 있었고, 데이터를 직접 세어서 잡았다.

### 버그 1 — stride 가 화면 포맷을 따라갔다

`setBuiltinCursor()` 가 `_outputPixelFormat.bytesPerPixel` 로 행 간격을
계산하는데, 커서 데이터는 **인덱스 1바이트/픽셀**이다. 알파 모드에서 화면이
32bpp 가 되자 간격이 4배로 벌어지고 픽셀은 1바이트씩 쓰여, 글리프가 4배 폭에
흩어지고 사이가 `0xFF`(투명)로 남았다.

### 버그 2 — 세로 복제가 2배만 알았다

```cpp
byte *dst2 = (sclH == 2) ? dst1 + 16 * sclW2 : dst1;   // 3배에서 틀림
```

3배에서 **세 행 중 두 행이 비었다**. 블록 복제로 일반화했다.

### 실측 (`~/games/curcheck.cpp`)

set 된 글리프 비트 하나는 `sclW * sclH` 개의 불투명 바이트를 만들어야 한다:

| 상황 | 기존 | 수정 | 기대 |
|---|---|---|---|
| 2배, 팔레트 화면 | 124 | 124 | 124 |
| **3배, 팔레트 화면** | **93** | **279** | 279 |
| **3배, 알파(32bpp)** | **12** | **279** | 279 |

`12` 는 실행 중인 게임에 프로브를 넣어 관측한 값과 정확히 일치했다 — 이게 증상과
stride 를 연결한 근거다. **2배는 양쪽이 동일**하므로 기존 플랫폼 동작은 불변이다.

### 미리 32bpp 로 구워두지 않는 이유

커서는 팔레트가 바뀌면 색이 바뀐다. 32bpp 로 구우면 페이드마다 다시 구워야 하고,
`CursorMan` 이 이미 커서 팔레트로 그 일을 한다. 인덱스로 두면 메모리도 1/4 이고
캐시 무효화 조건도 단순하다.

비용 실측: 48x48 = 2,304바이트, 30초에 약 100회 재생성 = 회당 수 마이크로초.
최적화할 것이 없다.

### 대조군

`ja-mi2` **diff=0**, `ja-zak` **diff=0**.

## S9 검증 기록 — 가변폭 (2026-09-06)

### 사용자 지적: "Indy3 는 글자가 겹치는 것 같은데"

맞았다. 폰트 metrics 를 직접 재서(`~/games/advancecheck.py`) 확인:

| 방식 | scale 2 | scale 3 |
|---|---|---|
| 내림 | **747**/2350 (32%) | **1221**/2350 (52%) |
| 올림 | 19 | 11 |
| **잉크까지 확장 후 올림** | **0** | **0** |

원인이 두 겹이었다:

1. **스케일 나눗셈 손실** — 폰트 metrics 는 확대된 픽셀 단위인데 엔진은 게임
   픽셀로 배치하고 다시 곱한다. 내림이면 문자당 최대 `scale-1` px 을 잃고,
   잉크가 advance 를 꽉 채우므로 다음 글자가 파고든다.
2. **폰트 자체 결함** — `vj00.fnt` 2350자 중 38자가 잉크를 advance 보다 1px
   넓게 구웠다. 반올림으로는 못 잡으므로
   `advance = max(advance, bearingX + inkWidth)` 로 런타임에 흡수.

대가는 문자당 최대 1 게임픽셀의 여유 간격. 겹치는 것보다 낫다.

### 사용자 지적: "글자 단위 vs 문자열 단위 폭 계산이 다르다"

실제 버그였다. 두 경로가 갈라져 있었다:

- 그리기: `printChar` → `advanceFor()`
- 측정: `getStringWidth` → **`getCharWidth()`** ← hi-res 를 몰랐다

`string.cpp:621` 의 `_nextLeft -= stringWidth / 2` 가 가운데 정렬에 쓰이므로,
그리기가 더 넓으면 자막이 밀려 화면 밖으로 나간다. `getCharWidth()`(V3 ·
Classic 양쪽)에도 같은 정책을 연결했고 계측 결과 **불일치 0건**.

### 실측 (Indy3 `vj00.fnt`, scale 2)

```
ADVANCE chr=0xD0B9 idx=893  fontAdv=18 -> 9  (game said 4)
ADVANCE chr=0xE2B1 idx=159  fontAdv=20 -> 10 (game said 4)
ADVANCE chr=0xE7B4 idx=446  fontAdv=21 -> 11 (game said 4)
```

글자마다 다르다. `metrics=game`(기본) 에서는 **호출 0회** — 기존 레이아웃 불변.

## 이번에 걸린 함정

- **`Common::INIFile` 은 `;` 를 줄끝 주석으로 취급하지 않는다.** `scale=3  ; 이유`
  → 값이 `"3  ; 이유"` 가 되어 조용히 무시(그래서 `scale=1` 이 나왔다).
  맵 생성기가 주석을 별도 줄에 쓰도록 고쳤다.
- **SDL 창 클래스는 argv[0] 에서 온다.** `/tmp/svm-work` 로 복사해 쓰면 클래스가
  `svm-work` 라 `xdotool search --class scummvm` 이 실패한다. 스크립트 **37개**를
  `find_window()`(xwininfo 로 루트의 첫 자식) 방식으로 일괄 수정.
- **`ja-zak` 40,895B 차이** → 재실행 104B, 세 번째 0B. 잡음 바닥은 66B.
  판정은 한 번의 비교로 하지 않는다는 원칙이 또 필요했다.
