## The open task: a heap overrun on 16-bit screens

**This is the next thing to do, and it is fully diagnosed. Do not re-derive it.**

### What is wrong

`engines/scumm/gfx.cpp:802`:

```cpp
if (_hiResText.alphaActive() && _hiResText.coverage()) {
    HiResTrueColorSink sink((uint32 *)_compositeBuf, ...);   // 4 bytes/px
```

`_compositeBuf` is allocated at `_outputPixelFormat.bytesPerPixel`
(`scumm.cpp:1950`). On a 16-bit screen that is 2 bytes per pixel, and the
sink writes 4. It runs off the end of the allocation by exactly the buffer's
own size.

### Three independent measurements, all agreeing

**1. The arithmetic** — `~/games/probes/overrun.cpp`, a transcription of the
allocation and the sink loop:

```
$ g++ -fsanitize=address -g -o /tmp/ovr ~/games/probes/overrun.cpp && /tmp/ovr
_compositeBuf = 128000 bytes (64000 px * 2 bpp)
writing 64000 px * 4 bytes = 256000 bytes
ERROR: AddressSanitizer: heap-buffer-overflow
WRITE of size 4 ... 0 bytes after 128000-byte region
```

**2. FM-Towns is safe by accident** — `~/games/sinkreach.py`:

```
cell        frames  hires   blending  TCSINK  format
towns-hr    3       yes     yes       0       RGB565@2
towns-noa   2       yes     no        0
dos-hr      2       yes     yes       4       ABGR8888@4
```

FM-Towns turns blending on at 16bpp and still never reaches the sink, because
`gfx.cpp:791` returns into `towns_drawStripToScreen` first. That return is the
only thing protecting it. DOS is the control: 32bpp, buffer and sink agree.

**3. PC-Engine reaches it and dies** — `~/games/pcesink.py`:

```
cell     frames  hires   blending  TCSINK  format
hires    0       yes     yes       2       RGB565@2
         TCSINK outBpp values: ['2']
         *** overrun reached ***
noalpha  1       yes     no        0
```

`frames 0` is the finding: the alpha cell captured no screenshot at all while
the control captured one. It writes past the heap and dies. PC-Engine has
`GF_16BIT_COLOR` and no early return, so nothing catches it.

### The fix

`engines/scumm/hires_sinks.h` already has the right class:

| sink | destination | `writeBlended` |
|---|---|---|
| `HiResIndexSink` | 8bpp | cannot blend, picks a side at 128 |
| `HiResPalette16Sink` | **16bpp** | `coverage >= 128 ? fg : bg` — a threshold |
| `HiResTrueColorSink` | 32bpp | real alpha blending |

**`HiResPalette16Sink` is never constructed by the engine.** Only
`test/engines/scumm/hires_sink.h` uses it. So the work is:

1. Choose the sink by `_outputPixelFormat.bytesPerPixel` at `gfx.cpp:802`,
   rather than assuming 32.
2. Give `HiResPalette16Sink::writeBlended` real blending instead of the
   threshold. 16-bit can blend: `colorToRGB` on both colours, weighted
   average, `RGBToColor` back — the same shape as `HiResTrueColorSink`, which
   is 20 lines below it. 5:5:5 gives coarser gradations than 8:8:8, but a
   gradation rather than a hard edge.

Note `_pal` differs between the two: `HiResPalette16Sink` takes
`const uint16 *` while `HiResTrueColorSink` takes `const uint32 *`
(`paletteCache()`). Check which one a 16-bit screen has filled — `_16BitPalette`
(`palette.cpp:368`) and `_paletteCache` (`hires_text.cpp:500`) are separate
tables and only one is maintained for a given configuration.

### How to verify the fix

```bash
# 1. re-apply the probes (they were removed; the tree is clean)
cd ~/src/scummvm
git apply ~/games/probes/tcsink.patch      # TCSINK at the sink site
git apply ~/games/probes/csprobe.patch     # CSPROBE in noteGameCharset

# 2. build, then:
python3 ~/games/pcesink.py     # must go from frames 0 to frames > 0
python3 ~/games/sinkreach.py   # FM-Towns and DOS must not change

# 3. remove the probes before committing
git checkout -- engines/scumm/gfx.cpp engines/scumm/hires_text.cpp
```

The closing condition is **`pcesink.py` capturing a frame with blending on**,
not merely `TCSINK` reporting a different number. A count that changes while
the process still dies proves nothing.

Also worth adding: a unit test in `test/engines/scumm/hires_sink.h` feeding
`HiResPalette16Sink::writeBlended` coverage 0/64/128/192/255 and asserting the
output is monotonic between background and text, rather than two values. The
existing `test_truecolor_sink_blends_between_the_two_indices` is the template.

## Correction worth carrying forward

**I twice reported a harness failure as a measurement.**

- `sinkreach.py` v1 passed both `-c` and `--config`, so ScummVM exited with
  `Option '--config' requires an argument`. Every cell read `TCSINK 0`, which
  looks exactly like "the code path is never taken".
- `sinkreach.py` v2 copied the real `scummvm.ini`, whose `ja-mi2` target
  points at font-less data, so hi-res never engaged and blending read `no` —
  contradicting a `townshook.py` log from an hour earlier that plainly said
  `blending into RGB565@2`.

Both were caught only by noticing that a *previous* run had said otherwise.
The rule already in the skill — grep for the program's own startup marker
before reading a log for feature evidence — would have caught both, and I
did not apply it. The current `sinkreach.py` prints frames and `hires`
separately for this reason, and refuses to run when the probe is absent.
